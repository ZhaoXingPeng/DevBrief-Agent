# GitHub Issue / PR 证据 SOP

本 SOP 是 DevBrief 的统一交付格式。目标是让 Reviewer 可以只看 Issue、PR 和评论，复现“为什么改、怎么改、证据是什么、失败如何恢复”。参考 BabelFLUX-java #123/#128 的中文 Gitmoji 标题、实验记录和回滚说明，并与 [`CONTRIBUTING.md`](../../CONTRIBUTING.md) 保持一致。

## 1. 工作对象

| 对象 | 只回答一个问题 | 必填结果 |
| --- | --- | --- |
| Proposal | 值不值得做？ | 用户问题、范围、非目标、成功标准、风险 |
| Design | 应该怎么做？ | 边界、候选方案、选择依据、契约/数据/安全影响、迁移 |
| Feature / Coding | 这次交付什么？ | Given/When/Then、测试边界、外部依赖 |
| Bug | 哪里错了，如何不再错？ | 最小复现、期望/实际、版本、根因、回归测试 |
| PR | 关联结果是否被证据证明？ | 实现、验证、实验、风险、回退、Review 处理 |

一个 Issue 只承载一个可独立验收的结果；“统一优化”“研究一下”“顺便重构”必须拆成多个 Issue。

## 2. 标题与正文

标题必须是 `<emoji> <type>(<scope>): <中文动词短语>`，例如 `🐛 fix(github): 修复幂等查询导致重复 Issue`。动词要具体，不超过 72 个字符，不在标题里写版本号或结果夸张词。

Bug 正文至少包含：

```markdown
## 问题
## 最小复现
## 期望 / 实际
## 影响版本或提交
## 根因假设
## 范围 / 非范围
## 验收
Given ...
When ...
Then ...
## 安全与脱敏
## 回归范围
```

Design / Feature 需要增加候选方案、取舍和契约影响。验收必须可执行，禁止用“体验更好”“性能提升”替代阈值或观测字段。

## 3. 开发与验证顺序

行为变化遵循 Red -> Green -> Refactor -> Full Check：

1. `RED`：先写失败测试，评论记录测试名和失败原因。
2. `GREEN`：实现最小行为，评论记录测试通过结果。
3. `REFACTOR`：整理边界和命名，不改变测试契约。
4. `FULL CHECK`：运行与风险相称的测试、lint、类型、构建和文档检查。

分支使用 `feat/<issue>-<topic>`、`fix/<issue>-<topic>`、`docs/<issue>-<topic>` 等短生命周期命名；一个分支和 PR 只关联一个 Issue。提交主题遵循仓库 Gitmoji 规范，并在正文写背景、变更、验证、Refs。

## 4. PR 首文与评论节点

PR 首文按以下顺序：

```markdown
## 关联 Issue
## 结论
## 范围 / 非范围
## 实现与架构
## 契约与兼容
## 实验记录
## 验证
## 风险与回退
## Review 处理
## 提交前检查
```

有结果就及时追加评论，不把所有事实留到最后一次总结。至少包含这些节点：

- `阶段：D0/D1`：设计或契约决定、被否决方案和理由；
- `阶段：RED`：失败测试与最小复现；
- `阶段：GREEN`：实现位置、通过测试和未覆盖边界；
- `阶段：D2/D3/D4`：fake、sandbox、real 实验；
- `阶段：验证收尾`：命令、结果、CI、审查意见和回退决定。

实验评论固定格式：

```text
阶段：<D0 设计 / D1 契约 / RED / GREEN / D2 fake / D3 sandbox / D4 real / 验证收尾>
假设：<要验证的命题>
环境：<commit、依赖、provider/模型版本；不含秘密>
输入：<规模、fixture 版本、脱敏描述>
命令：<可复制命令>
结果：<断言、计数、时延、artifact 摘要；不含完整私有内容>
结论：<接受、拒绝、阻塞或下一步>
限制：<不可外推范围与剩余风险>
```

Bug 修复要补 STAR：`Situation` 说明现象/影响，`Task` 写验收阈值，`Action` 写根因修复和测试，`Result` 写真实数据、回归和剩余风险。

## 5. Review 与回复

Review 顺序固定为行为/边界/安全 -> 契约兼容 -> 测试/实验 -> 文档 -> 风格。评论前缀只使用 `blocking:`、`question:`、`suggestion:`、`nit:`、`praise:`。作者回复不能只写“已修改”：必须写文件/位置、实际验证，或说明不采纳理由和后续 Issue。关键行为改动重新 Review。

## 6. 外部写与敏感数据

真实 provider、音频、GitHub sandbox 必须标记 E3/E4 证据等级，并记录环境、输入范围、结果和不可外推边界。token 只注入进程环境；禁止进入代码、评论、trace、SQLite、截图或 Issue/PR 正文。原始音频、完整转写和私有 Issue 内容只保留在受控实验环境。外部写必须有明确审批、plan hash、幂等键、checkpoint、回执和 query-first 恢复；禁止自动关闭 Issue、合并 PR、创建分支或执行 shell。

## 7. 合并门禁

PR 合并前必须有：关联 Issue、通过 CI、实际命令与结果、实验/未覆盖范围、风险与回退方式、未提交秘密确认。默认 squash merge 并删除分支。合并后核对 `main`、Issue 状态、文档链接和工作树，保留用户未跟踪文件，不用清理命令覆盖它们。
