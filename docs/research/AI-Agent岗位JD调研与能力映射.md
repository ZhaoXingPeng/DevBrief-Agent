# AI Agent 岗位 JD 调研与能力映射

**版本：** 0.1-draft
**采集快照：** 2026-09-08（Asia/Shanghai）
**用途：** 为 DevBrief Agent 的技术选型、迭代优先级、Demo 证据和简历表述提供依据；不是招聘信息聚合页，也不代表任何公司的完整岗位库存。

## 1. 结论先行

当前大型互联网公司的 Agent 岗位，已经不把“会调用大模型 API”当作核心区分项。反复出现的硬要求是：

1. **Agent Harness / Runtime：** 状态、上下文、任务规划、工具编排、循环控制、中断恢复和并发调度。
2. **评测闭环：** 有标注样本、离线 Eval、回归、A/B、失败归因和数据版本，而不是只展示一次成功 Demo。
3. **生产工程：** Python 或 Go/Java，服务化、云原生、可观测性、性能/成本、稳定性和故障排查。
4. **安全边界：** 工具权限、网络隔离、沙箱、提示注入防护、受控写入和审计。
5. **业务闭环：** 能把一个具体场景拆成可验证任务，并以准确率、成功率、时延、成本或人工效率说明价值。
6. **可复用资产：** 工具协议、任务模板、组件、文档、样例和开源贡献，而不是一次性的 Prompt。

因此，DevBrief 的正确定位不是“语音会议纪要”，而是：

> 一个以语音/转写为输入，面向研发任务的可恢复 Agent Harness 示例：从证据提取、工具调用、审批写入到 trace 回放和评测回归形成闭环。

语音是有辨识度的输入适配器，但不应遮蔽 Agent Runtime、质量和安全这些对岗位更有解释力的主体能力。

### 4.1 京东样本的信号

1. **Agent Loop 是基本结构，不是选配。** 规划、工具调用、多轮/长程任务、状态和记忆在多个岗位中同时出现。

## 7. 对 DevBrief 的岗位定位

### 7.1 推荐主线

**目标岗位：** Agent 平台/Harness、Agent 后端、AI Testing/质量 Agent、AI Coding/研发效能 Agent。
**次级覆盖：** 大模型应用工程师、RAG/工具编排工程师。
**不应主张：** 已完成 Agentic RL、SFT/RL 训练基础设施或大规模多 Agent 调度，除非后续有独立实验、数据和报告支撑。

理由是：DevBrief 的“语音决策到研发任务”天然包含不确定输入、证据检索、外部写入、权限、失败恢复和审计，能在一个狭窄但真实的场景中展示岗位最关心的工程闭环。

### 7.2 当前已定义但尚未实现的能力

仓库当前处于 Phase 0.1，已有规范、需求、功能验收、Harness 架构、状态/审批契约和系统上下文文档；没有可运行服务。下面的“已有”只能用于设计说明，不能在简历中写成已交付功能。

## 8. 作品集验收口径

简历项目不应以“接入了 LangGraph/MCP/RAG”收尾，而应该能当场演示和复查以下事实：

1. 输入一份带歧义的研发会议转写，系统会产生结构化候选并标记未知字段，而非猜测负责人/期限。
2. 运行时能展示状态迁移、证据来源、工具调用、policy 结论和 approval 绑定的精确计划哈希。
3. 模拟中断或 provider 超时后，恢复逻辑不会重复创建 Issue；未知写入结果会先查询而非盲重试。
4. 修改任务草稿后旧批准立即失效；未批准的外部写不可调用。
5. 对同一固定样本集可以运行 Eval，并输出样本版本、模型/提示词版本、字段指标、证据覆盖、失败分类。
6. Demo 默认不需要真实 GitHub token、真实音频或在线模型；真实集成单独标记为实验环境。

这些证据可同时覆盖字节的 Harness/AI Testing/AI Coding 样本、京东的 Agent 架构/数据/安全样本，以及百度的智能体/大模型工程/AI 测试样本。

## 9. 简历表述边界

在实现和测试完成前，使用“设计/规划中”描述；不要使用“搭建完成”“提升 xx%”“支持生产”等完成式表述。完成后可按证据替换为：

```text
构建面向研发 Bug Triage 的可恢复 Agent Harness：以类型化状态机编排
证据检索、计划、审批与 GitHub Issue 写入；实现 checkpoint、幂等回执和
失败回放，并通过版本化 Eval 集报告字段准确率、证据覆盖与回归结果。
```

其中“实现”和“报告”的前提是仓库中确实存在可运行命令、测试、样本和生成报告。没有真实基线时，不填充虚构的准确率、时延、成本或用户收益。
